# 渠道经营观察设计

## 目标

把现有“渠道价格对比”改造成管理员专用的“渠道经营观察”：管理员能维护每个 Token 模型的上游采购价，直观看到渠道成本、销售收入、盈利、实际使用和质量风险，并据此手工调整渠道优先级或停用渠道。

## 已确认范围

- 仅管理员可见菜单、页面和接口；普通用户菜单中无入口，直接访问返回 403。
- 先覆盖按 Token 计费的模型；图片、音频、视频等其他计费方式不在本次范围。
- 站内与上游均按美元 1:1，所有金额统一显示美元，不换算人民币。
- 页面只给管理建议，不自动修改优先级、不自动停用或删除渠道模型。
- 复用并改造现有 `/channel-price-compare` 页面，不新增第二套功能重复的页面。

## 价格维护

渠道编辑页在已选模型区域增加：

- 上游计费分组；
- 每个站内模型对应的上游模型名（来自现有模型映射，只读展示）；
- 输入、输出、缓存读取、缓存写入采购价，单位均为美元 / 1M Token；
- 自动探测价与手工维护价的差异提示。

采购价保存在渠道现有 `settings` JSON 中，不新增数据库表或字段。价格以站内模型名为键，避免修改模型映射后历史统计失去归属。保存时拒绝负数，并删除已从渠道移除模型的孤立价格。

价格使用顺序：

1. 手工维护价优先，作为成本与盈利计算依据；
2. 未维护手工价时，使用自动探测价；
3. 两者都没有时明确显示“价格未维护”，不计算虚假成本或盈利。

自动探测价始终单独展示。手工价与探测价不一致时标记价格差异，便于管理员核对上游后更新维护价。

## 调度状态

以 `abilities`（模型渠道能力表）中的实际分组、模型、启用状态、优先级和权重为准：

- 同一服务分组和模型中最高优先级的唯一渠道标记“主用”；
- 最高优先级存在多个渠道时均标记“主用池”，并显示权重；
- 低优先级渠道标记“备用”；
- 今日请求统计显示实际命中分布，避免把优先级配置误称为唯一实际渠道；
- 每行提供带模型和渠道筛选条件的日志入口，供管理员定位具体用户投诉。

## 经营指标

页面顶部固定显示北京时间今日汇总：

- 销售额；
- 预估上游成本；
- 预估盈利；
- 毛利率；
- 风险渠道数。

第一层按渠道汇总，支持按成本、收入、盈利、毛利率、请求数和风险排序。每个渠道显示累计与今日两组指标：

- 销售额：消费日志 `quota / QuotaPerUnit`；
- 请求数：成功消费请求数；
- 预估上游成本：按输入、输出和日志中可取得的缓存 Token 乘当前有效采购价；
- 预估盈利：销售额减预估上游成本；
- 毛利率：预估盈利除以销售额。

第二层按模型展开候选渠道，横向比较服务分组、上游分组、调度状态、优先级、权重、采购价、自动探测价、本站售价、今日实际命中、累计/今日经营指标和 24 小时质量。

历史请求没有采购价快照，因此累计成本按当前有效采购价估算，界面必须使用“预估”字样，不宣称是历史实际结算成本。

## 质量观察与建议

近 24 小时按渠道和模型汇总成功请求、错误请求、成功率、平均耗时、最后错误时间与摘要。建议只基于可解释事实生成：

- 采购价缺失：建议补充价格；
- 毛利为负：建议调价或检查后停用；
- 毛利率低于现有 60% 目标：建议检查售价或采购渠道；
- 有足够请求样本且成功率偏低：建议降低优先级或检查后停用；
- 自动探测价与手工价不一致：建议核对上游价格。

建议不触发任何写操作。管理员通过“编辑渠道”或“查看日志”完成最终判断和操作。

## 页面结构

1. 标题与筛选：服务分组、模型、渠道、经营/质量状态。
2. 今日总览卡片：收入、成本、盈利、毛利率、风险数。
3. 渠道经营汇总表：累计与今日并列，可排序，风险优先突出。
4. 模型渠道对比：按模型折叠，候选渠道按优先级降序。
5. 行内入口：编辑渠道、查看筛选后的日志。

界面沿用现有后台的卡片、表格、徽标和颜色变量，采用高信息密度的运营台风格；成本、收入和盈利使用稳定且可区分的语义色，风险只在需要管理员处理的行突出。所有新增文案进入现有 i18n。

## 后端与接口

扩展现有 `GET /api/channel/price_compare` 管理员接口，返回：

- 今日汇总；
- 渠道汇总；
- 按模型分组的渠道明细；
- 手工价、探测价、有效价及价格来源；
- 调度角色；
- 累计、今日、24 小时统计；
- 建议代码与说明。

继续使用 `AdminAuth`（管理员鉴权）和 `ChannelRead`（渠道读取权限）。接口不返回渠道密钥、上游访问令牌或其他敏感配置。渠道价格写入继续通过现有渠道更新接口和 `ChannelWrite`（渠道写权限）。

聚合查询使用 GORM 和 SQLite、MySQL、PostgreSQL 分别适配的日志 JSON 取值表达式，不依赖单一数据库方言。自动探测失败不阻断整个报告：有手工价则继续计算，没有则返回未知价格与探测错误。

## 验收

- 普通用户看不到菜单；直接访问页面跳转 403；直接调用接口被拒绝。
- 管理员可在渠道编辑页保存并再次读回采购价和上游计费分组。
- 手工价优先于探测价；缺手工价时使用探测价；全部缺失时利润为空。
- 主用、主用池、备用与实际选路规则一致。
- 累计/今日的销售额、请求数、预估成本、预估盈利和毛利率在固定样例中精确匹配。
- 页面能按渠道查看总体经营结果，并按模型比较候选渠道。
- 24 小时质量与建议在价格缺失、负毛利、低毛利和低成功率样例中正确。
- 浏览器真实操作验证价格维护、筛选、排序、展开、编辑入口和日志入口。

## 数据库变更

无数据库结构变更。采购价使用渠道现有 `settings` JSON 持久化。
